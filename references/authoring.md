# 写作与测试方法

## 一、description 怎么写

它是**唯一**决定「模型会不会想起这个技能」的东西。正文再好，description 不行就没人用。

**公式**

```
[做什么]。[什么时候用：场景 + 典型说法]。适用于：[3–5 个关键触发词]。
```

**三条原则**

1. **写触发条件，不写功能介绍。** 「整理读书笔记」比「一个强大的文献处理工具」有用。
2. **用用户的话，不用术语。** 用户说「把这本书整理一下」，不会说「执行文献结构化归纳」。
3. **适度推一把。** 模型倾向**少触发**；description 略主动更安全，但别堆到关键词堆砌。

**自检三问**

- 陌生人看这段，能判断什么时候该用它吗？
- 把技能名遮住，还能判断吗？
- 有没有 3 个以上**近邻但不该触发**的场景？写进正文的「不用」区。

## 二、测试怎么做

**最小测试（永远做）**

1. 准备 2–3 个**用户真的会说的话**
2. 加载技能跑一遍，不加载跑一遍（基线）
3. 并排看：好多少？差在哪？

两者差不多 → 技能没价值，或该写得更短。

**触发测试（最容易被忽略）**

- **该触发** 8–10 条：正式 / 口语 / 含错别字 / 不点名技能
- **不该触发** 8–10 条：**近邻场景**（用了同样的词，其实是别的事）

命中率低 → 改 description，**不要改正文**。

**进阶：A/B 盲测** —— 两个版本的结果去掉标签让用户选。人一旦知道哪个是新版就会偏爱新版。

**进阶：量化** —— 通过率 / 耗时 / token，和基线比。模型升级后重跑，**回归就是这样发现的**。

## 三、什么该进 references/

| 内容 | 放哪 | 原因 |
|---|---|---|
| 主流程、完成标准、边界 | SKILL.md | 每次都要 |
| 长清单、模板、范例全文 | references/ | 按需 |
| 平台差异表 | references/ | 按需 |
| 可复用脚本 | scripts/ | 直接执行，不进上下文 |

**判断标准**：每次执行都要读 → 正文；只有部分情况要读 → references。

## 四、写法细节

**写中文技能的三个注意**

1. 专有名词（技能名、命令、路径）保持英文，其余中文。
2. 别用「——」当结构，用序号、列表、小标题。
3. 示例要覆盖口语和书面语两种说法。

**执行原则**

- 说清 why，不要堆 MUST。解释清楚理由，模型才能泛化。
- 祈使句、高密度。一句能说清就别写两句。
- 删掉模型默认就会做的废话（no-op）——写之前问：这条不写会怎样？不会怎样就删。

## 五、评分要防「表面合规」

| 判定 | 含义 |
|---|---|
| **通过** | 有证据表明目标达成 |
| **失败** | 无证据 / 证据矛盾 / **证据是表面合规**（文件名对但内容空、格式对但逻辑错） |

**宽松的断言比没有断言更危险**——它给人虚假的信心。发现断言太松要指出来。

同时要**提取隐含声明并核实**：输出里说「用了 X 方法」「字段都填对了」，要回产物验证；验证不了的标「无法验证」。

## 六、粒度：拆还是合

依据：SkillsBench（2026-02）结论是**小而模块化（2–3 个模块）优于大型内容堆**；一次真实重构把 47 个技能合并回 12 个。

**按能力拆，不按业务拆**

- ❌「登录需求拆解」「订单需求拆解」「支付需求拆解」——描述几乎一样，AI 必然选错
- ✅「需求拆解」一个技能，业务差异用输入参数区分

**判断标准**：值得分享给别的团队用吗？值得 → 粒度大概率对；只在当前项目能用 → 可能太细。

**两层结构**：真实案例 87 个技能共 898 KB 压垮上下文，改成「轻 SKILL.md + 详 references」后降到 27 KB（-97%）。

**该合并的信号**

- 几个技能从来没被单独用过（总串起来用）
- description 互相重叠
- 一个的产出正好是另一个的输入，中间不需要人

**阈值**：行数、token、description 长度以 `references/checklist.md` 为准。

## 七、自由度与精简（OpenAI Codex 的做法）

**前提：上下文窗口是公共资源。** 默认假设「模型已经够聪明」，只补它不知道的东西。每写一句都问：
- 模型真的需要这个解释吗？
- 这段值它的 token 吗？

### 按任务脆弱度选择自由度

| 自由度 | 写法 | 什么时候用 |
|---|---|---|
| **高**（文字说明） | 只写原则和判断依据 | 多条路都行、依赖上下文、靠启发式 |
| **中**（伪代码/带参脚本） | 给出推荐模式 + 参数 | 有偏好做法，但允许变化 |
| **低**（固定脚本、少参数） | 必须按这个顺序、这个命令 | 操作脆弱易错、必须一致 |

比喻：窄桥要护栏（低自由度），旷野随便走（高自由度）。**别给旷野装护栏，也别让窄桥没护栏。**

### references 的三条硬规则

1. **只一层深。** 所有参考文件都直接从 SKILL.md 链接，不做 `references/a/b/c` 的深链。
2. **超过 100 行要给目录。** 让模型预览时知道全貌。
3. **超过 1 万字要给 grep 关键词。** 在 SKILL.md 里写「搜什么能找到相关段落」。

### 三种渐进式披露写法

| 模式 | 结构 | 适用 |
|---|---|---|
| **总览 + 参考** | 正文给快速上手，进阶指向 FORMS.md / REFERENCE.md / EXAMPLES.md | 单一领域，功能分层 |
| **按领域分文件** | 正文给导航，`references/` 按领域拆（finance.md / sales.md / product.md） | 多领域，互不相关 |
| **按条件分文件** | 正文给基础，特定场景指向 REDLINING.md / OOXML.md | 常用简单、偶发复杂 |

### 技能目录里不要放的东西

README.md、INSTALLATION_GUIDE.md、QUICK_REFERENCE.md、CHANGELOG.md——**这些是给人看的，会白占上下文**。技能里只放 AI 干活需要的东西。

### 信息不重复

同一份信息只活在 SKILL.md **或** references 里，不要两处都有。细节优先放 references，正文保持精简。
## 八、五种结构模式（官方最佳实践）

不是每个技能都要全用，按任务挑。

| 模式 | 干什么 | 什么时候用 |
|---|---|---|
| **常见坑（Gotchas）** | 列出「不告诉就会做错」的具体事实 | **最高价值**，几乎每个技能都该有 |
| **输出模板** | 给具体结构，比用文字描述格式可靠 | 产出格式固定时 |
| **分步清单** | 让模型自己勾进度，防漏步 | 多步骤、有依赖或验证关卡 |
| **验证循环** | 做完→跑校验→修→再校验，通过才继续 | 有可执行的校验手段时 |
| **计划-验证-执行** | 先出中间计划→对照真源校验→再执行 | **批量或不可逆操作**（改文件、迁移、填表） |

### 常见坑怎么写

写「环境特有的、违反常识的事实」，不是通用建议。

```markdown
## 常见坑

- `users` 表是软删除，查询必须带 `WHERE deleted_at IS NULL`，否则会把停用账号算进来。
- 用户 ID 在数据库里叫 `user_id`、在认证服务里叫 `uid`、在计费 API 里叫 `accountId`，是同一个值。
- `/health` 只要 Web 服务活着就返回 200，数据库挂了也是 200。查完整健康用 `/ready`。
```

**放在 SKILL.md 里**，不要放 references——模型遇到问题前不会想到去加载。
**每次被纠正，就把这条纠正加进常见坑**，这是最直接的迭代改进。

### 另外三条

| 原则 | 反例 | 正例 |
|---|---|---|
| **给默认值，不给菜单** | 「你可以用 pypdf、pdfplumber、PyMuPDF 或 pdf2image…」 | 「用 pdfplumber 抽文字；扫描件需要 OCR 时改用 pdf2image」 |
| **教方法，不教答案** | 「join orders 和 customers，筛 region='EMEA'，sum(amount)」 | 「1 从 schema 找表 2 按 `_id` 约定 join 3 把用户条件转 WHERE 4 聚合数值列」 |
| **只补模型不知道的** | 解释「什么是 PDF」「HTTP 怎么工作」 | 只写项目约定、领域流程、不明显的边界情况 |
